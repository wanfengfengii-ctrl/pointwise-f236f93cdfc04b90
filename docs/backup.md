# 在线备份维护说明

目录库保存版本号、快照集合和“版本—分区—不可变对象”映射；对象文件名是载荷的 sha256，相同载荷可跨分区、跨版本共用。写入新版本只新增 manifest 行，不修改已有对象；因此同一对象可能先被回收规划为候选、随后又被新版本再次引用。

## 成功备份的含义

一次备份以 `backup.selected` 事件里的版本为声明版本。成功备份必须同时满足：

1. 恢复目录的当前版本（head）等于声明版本；
2. 默认读取得到声明版本的完整行集合（分区、ID、值），不接受摘要正确或文件存在作为替代；
3. 恢复后目录的 manifest 只引用本次备份实际复制并通过摘要核验的文件。

仅比较文件摘要或行集合都不够：若目录克隆晚于版本选择，恢复目录可能处于更晚版本；当新版本恰好重新引用了相同载荷（例如 `return` 批次），行集合与摘要都会正确，但目录版本已不等于声明版本，当前版本读取会因缺少新对象而失败。

## 保护：取得、移交、释放

备份不得以暂停提交或暂停回收来维持一致，也不得在复制载荷期间持有目录写事务（前台 `read` 的长事务不能借用为保护方案）。

- **取得**：备份在同一个短目录事务内读取当前版本与该版本 manifest，并在目录库中登记一条保护记录（保护所有者为本次运行，内容为声明版本）。事务提交后保护即生效，复制阶段不再持事务。
- **移交**：完成标记（`complete.json`，含版本与文件摘要列表）与备份目录内的目录副本共同构成该备份自身的依据；源侧保护释放后，已完成备份与源目录相互独立，源表继续提交不影响已完成副本。
- **释放**：写完完成标记后，以新的短事务删除保护记录；`finally` 中再做一次幂等删除，确保受控复制失败也会释放。释放必须先于对外宣告备份完成，或与之同批完成，不能遗留永久保护。

## 回收：候选与裁决

`plan` 产生候选时必须把“当前版本引用的对象”与“所有有效保护记录引用的对象”一起排除。候选产生后仍允许提交、备份和回收交错，因此候选名单只是提示，不是授权：

`sweep` 对每个候选在独立的短事务内、删除之前重新读取当前版本与保护记录，重新裁决。已经重新活跃或受保护的候选必须跳过（不删除，也不计入 `removed`）；只有裁决为死且无保护的文件才删除。删除后新的提交若再次引用该载荷，会因对象缺失而读取失败，因此裁决顺序不能颠倒为“先删后查”。`collect` 是 `plan` 与 `sweep` 的连续执行，同样受该规则约束。

## 恢复与拒绝

`restore` 仅接受带完成标记的备份，并在创建目标目录之前完成全部核对：完成标记存在；完成标记的版本等于备份目录副本的 head；完成标记列出的文件集合等于该版本 manifest 的对象集合；每个文件摘要匹配。任一不满足即拒绝，不得返回 head 与声明版本不同的湖。拒绝时不创建或保留恢复目录。

## 受控复制失败

`fail_at` 是从 0 开始的复制序号（文件按文件名排序、去重后计数）；序号等于文件数时不注入失败，备份正常完成。复制失败不产生完成标记，`restore` 因缺少完成标记而拒绝恢复，且不会创建恢复目录。

失败目的地会留下目录副本、已复制的部分载荷和 `events.json`（末尾含 `backup.failed`，错误类型来自实际异常）。`exist_ok=False` 使同一路径不能直接重试。责任划分：

- 备份任务：在 `finally` 释放保护，保留失败现场与事件日志，不自动删除现场；
- 维护负责人：确认无完成标记后删除失败备份目的地，需要重试时使用新路径；
- 恢复方：只负责拒绝不完整目录，不负责清理源侧残留。

## 值班检查

- 原回归：`python3 checks.py verify`（正常提交、历史读、静止备份、复制失败断言）。
- 原失败证据：`python3 checks.py repro` 应继续输出 `BACKUP_RESTORE_MISMATCH` 并以 1 退出；这不是待修测试。
- 审查重放：`python3 evidence_gate.py verify` 重跑回归与 `review_cases.json` 并核对 `review.json`；`python3 evidence_gate.py demo` 展示真实恢复行、版本和事件顺序。
- 人工验收至少抽查一次“恢复目录当前版本 == 声明版本”，而不只是把恢复行与期望行对比。
